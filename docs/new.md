Вариант A — выпуск сертификатов после обновления DNS-кэша (http-01)

Цель: дождаться, когда все резолверы начнут выдавать правильный A‑запись IP (45.12.108.8), и затем выпустить сертификаты через Certbot + Nginx.

Предпосылки
- Docker и приложения уже работают за Nginx (admin: 127.0.0.1:3000, pos: 127.0.0.1:4000).
- В Nginx есть серверные блоки на 80 для доменов, и Nginx активен.

1) Проверка DNS до обновления кэша
- Ожидаемое значение A для доменов: 45.12.108.8
- Команды для проверки с популярных резолверов:
  - `dig @1.1.1.1 admin.wincs.uz A +short`
  - `dig @8.8.8.8 admin.wincs.uz A +short`
  - `dig +trace admin.wincs.uz A` (показывает авторитетный ответ)
- Если какой‑то резолвер показывает старый IP, подождите до истечения TTL (у записи был TTL 14400 секунд ≈ 4 часа).

2) Базовый HTTP‑доступ перед выпуском сертификата
- Убедитесь, что порт 80 открыт (провайдерский фаервол/SG) и Nginx слушает 0.0.0.0:80 и [::]:80:
  - `sudo ss -ltnp | grep ':80 '`
- Быстрая проверка доступности с внешней машины:
  - `curl -I http://admin.wincs.uz` (должен отвечать без timeout)

3) Выпуск сертификата для админки
- После того как оба резолвера (1.1.1.1 и 8.8.8.8) возвращают 45.12.108.8:
  - `sudo certbot --nginx -d admin.wincs.uz`
- При вопросе о редиректе выберите перенаправление на HTTPS.
- Проверка:
  - `curl -I https://admin.wincs.uz`
  - `sudo ss -ltnp | grep ':443 '` (Nginx должен слушать 443)

4) Выпуск сертификата для POS
- Убедиться, что есть серверный блок на 80: `server_name pos.wincs.uz; proxy_pass http://127.0.0.1:4000;`
- Выпустить сертификат:
  - `sudo certbot --nginx -d pos.wincs.uz`
- Проверка:
  - `curl -I https://pos.wincs.uz`

5) Автопродление и обслуживание
- Проверить таймер обновления сертификатов:
  - `systemctl status certbot.timer`
- Тест ручного обновления (dry‑run):
  - `sudo certbot renew --dry-run`
- При обновлении кода:
  - `git pull && docker compose build --pull --no-cache && docker compose up -d`
  - Миграции: `docker compose exec admin npm --workspace=@mini/db run migrate:deploy`

6) Если снова видите timeout при валидации
- Почти всегда это DNS‑кэш/TTL. Повторно проверьте `dig` у 1.1.1.1 и 8.8.8.8.
- Убедитесь, что в провайдерском фаерволе открыты 80/443 (IPv4 и, если есть, IPv6) для всех.
- Альтернативы без ожидания TTL:
  - Временный поддомен с малым TTL (например, `admin2.wincs.uz`) → выпустить cert, затем перевыпустить для боевого домена.
  - DNS‑challenge через TXT‑записи (потребуется ручной ввод или API‑плагин DNS).
